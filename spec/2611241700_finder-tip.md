# 视频号：首次进入的缓存完整性说明

## 需求

视频号的缓存是微信「边播边写」的产物：只有用户在微信里把视频完整播放过一遍，文件才会被写完整。
本应用只读 `cache/<hash>/finder/video` 下已有的文件，不会、也无法替用户补下载。

于是没完整播放过的视频会以各种「坏样子」出现在列表里：

- 列表页渲染首帧失败，只剩灰色占位；
- 文件不完整，点开播放到中途报错或卡住；
- 导出得到的文件同样不完整，换了播放器也打不开。

这些现象看起来像应用的 bug，实际是缓存本身没写完。之前的界面没有任何提示，用户只能猜。
本次在视频号标签页首次进入时弹一次说明，把「先看完、再导出」这个用法讲清楚，并提供
「不再显示」复选框，读过的用户可以永久关掉。

## 交互

- 触发：`SourceTab.FINDER` 首次加载时弹出，弹窗叠加在列表之上，不阻塞数据加载
  （列表在弹窗后面正常取，关掉即可看到内容）。
- 关闭：只有一个确认按钮「我知道了」；返回键、点击弹窗外部同样关闭。
- 三种关闭方式都按当时的复选框状态生效：勾了「不再显示」就写入偏好，之后启动、
  切账号都不再弹；没勾则只在本次进程内不再打扰，下次启动仍会提示。
- 为什么做成「按勾选状态生效」：文案是纯告知，没有「确认/取消」的语义对立；
  反过来「勾了却没记上、下次又弹」比「点了外部却记住」更让人困惑。

弹窗正文用四段：结论（缓存要靠微信播完整）→ 三种典型症状 → 用法（看完再下拉刷新）→
免责（已看完的不受影响）。症状用 `·` 起头分行，方便扫读；小屏上正文可滚动，不会撑破弹窗。

底部操作区是**一行**：左边「不再显示」复选框，右边「我知道了」按钮。
没有用标准 `AlertDialog`：它把按钮统一右对齐，复选框塞进按钮区只能单独占一行，
正文下方会空出一大块。这里改用 `Dialog` + `Surface` 自绘容器，尺寸约束照抄 M3
（宽 280–560dp、圆角 28dp、`surfaceContainerHigh` 底色），布局完全可控。

## 实现

- `SettingsRepository.finderTipDismissed`：偏好键 `finder_tip_dismissed`，全局一份，
  与账号无关（说明内容不随账号变化）。
- `GalleryUiState.showFinderTip`：是否显示弹窗。
- `GalleryViewModel.load()`：进入时算一次
  `tab == FINDER && !finderTipShown && !settings.finderTipDismissed`，
  并把 `finderTipShown` 置真。ViewModel 按「账号 + 标签页」缓存在 `ViewModelStore` 里，
  切走再回来是同一个实例，所以用实例字段就能兜住「同一次使用里只弹一次」。
  换账号会新建 ViewModel，会再弹一次——这是有意的，新账号的缓存同样是另一套。
- `GalleryViewModel.dismissFinderTip(permanently)`：关状态，`permanently` 为真时写偏好。
- `GalleryScreen.FinderTipDialog`：`Dialog` + `Surface` 自绘容器，底部一行放 `Checkbox`
  与确认按钮；文案见 `strings.xml` 的 `finder_tip_title` / `finder_tip_message` /
  `finder_tip_dont_show` / `finder_tip_confirm`。

刷新、排序、分页都不重新计算 `showFinderTip`，避免下拉刷新时再弹一遍。

## 文案

- 标题：关于视频号缓存
- 正文：
  > 视频号的视频不会边播放边保存完整文件。只有在微信里完整播放过一遍，视频缓存才会被完整写入本机；
  > 本应用只读取这份缓存，不会替你下载。
  >
  > 没有完整播放过的视频，可能出现：
  > · 列表里渲染不出首帧，只显示灰色占位
  > · 视频不完整，播放到中途出错或卡住
  > · 导出的文件同样不完整，打不开
  >
  > 用法：先在微信里把要看的视频完整看完，再回到这里下拉刷新列表，即可正常预览与导出。
  > 已经完整播放过的视频不受影响。
- 复选框：不再显示
- 按钮：我知道了

## 验证

- `compileDebugKotlin` 通过。
- 真机：首次进入视频号页弹出；点「我知道了」后切到别的标签页再切回不弹；
  勾选「不再显示」后重启应用不再弹。
