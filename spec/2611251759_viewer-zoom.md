# 图片大图页：双指缩放与放大后拖动

## 需求

大图页此前只能看、不能放大：截图里的字、照片里的细节都看不清。要的是相册式交互——
双指放大缩小、放大后单指拖动看局部，并且不能把原来的左右滑动翻页弄坏。

表情包（wxgf / GIF）跟旋转一样不参与，只有静态图片 JPEG / PNG / WEBP 有这套手势。

## 倍率

- 上限 4 倍（`MAX_IMAGE_SCALE`）。微信与各家系统相册多在 3~5 倍，取中间值。
- 下限就是 1 倍，也就是放大前的 Fit 大小（`MIN_IMAGE_SCALE`），永远不允许比原来看起来更小。
- 捏到 1~1.15 倍之间松手，140ms 动画吸附回 1 倍并居中，避免卡在 1.05 倍把翻页锁住。

## 手势与翻页怎么共存

用 `awaitEachGesture` 自己识别，只在两种情况下消费事件，其余一律放行给 `HorizontalPager`：

- 触点 ≥ 2：立刻按双指缩放/平移处理；
- 已经放大且单指拖动超过 `touchSlop`：接管成平移。没过 slop 之前不消费，
  所以点按切换工具条、点顶栏按钮都不会被抢走。

只消费还不够，放大时还要把翻页锁住：`HorizontalPager(userScrollEnabled = zoomedKey != current.key)`。
各页自己放大时通过 `snapshotFlow` 上报，页面被回收（`DisposableEffect.onDispose`）时补一条「已缩回」，
否则锁会留在父层，翻页一直卡着。这就是微信与系统相册的做法：放大状态先缩回，再翻页。

## 缩放与平移的换算

`zoomTransform` 是纯函数，单独可测：

- 绕双指中心缩放：`offset' = offset * k + (centroid - center) * (1 - k) + pan`，焦点下那块画面保持不动；
- 位移夹在「内容不露出黑边」的范围内，内容比视口小时（小图放大后仍比屏幕窄）锁在中心；
- 旋转 90/270 度时内容在屏幕上的宽高是互换的，边界按互换后的尺寸算，否则会允许把画面拖出黑边。

绘制层顺序是「外层缩放/平移 → 内层旋转」：平移始终是屏幕坐标系，
转过 90 度以后往右拖还是往右走，不会变成上下移动。工具条不在这一层里，所以旋转、缩放都不影响它们的位置。

## 踩坑：单指拖动一松手图片就整个消失

真机上必现：双指放大后用单指拖，松手瞬间图片变全黑，顶栏和按钮还在；再捏一下或点旋转按钮能救回来。

原因在抬手那一帧。`PointerEvent.calculateCentroid()` 只统计 `pressed` 的指针，
最后一帧所有手指都抬起了，质心返回 `Offset.Unspecified`（NaN）。单指分支当时只判断
「已经超过 slop」，没有判断这一帧还有没有手指，于是拿 NaN 质心算了一次：

```
pivot = NaN - center              // NaN
moved = offset * 1 + pivot * (1 - 1) + 0
      = offset + NaN * 0          // NaN（NaN 乘以 0 还是 NaN）
```

`offset` 变成 NaN 后写进 `graphicsLayer` 的 `translationX/Y`，这一层就不再绘制，图片消失。
双指分支没这个问题：抬手帧 `calculateZoom()` 返回 1、`calculatePan()` 返回 0，
条件 `zoom != 1f || pan != Offset.Zero` 不成立，压根没调 `onTransform`。

修法两道：

1. 手势循环里只看 `pressedCount > 0` 的帧，抬手帧不处理；
2. `zoomTransform` 对质心、位移、倍率做有限性校验，NaN 输入直接返回上一个状态。
   这层是防御——就算将来别处再喂进 NaN，也只是这一帧不生效，不会把图片画没。

## 验证

- 单测新增 `ViewerZoomTest`：绕中心/绕角缩放、4 倍上限、最小 1 倍、拖动夹紧、
  小图居中、NaN 质心与 NaN 位移不污染状态；反向验证：去掉防护后 `resultIsAlwaysFinite` 失败。
- `lintDebug` 无告警，四 ABI `assembleDebug` 通过，单测 165 条全绿。
- 真机：双指缩放跟手、4 倍封顶、拖到边缘不露黑边、缩回 1 倍恢复翻页；
  单指拖动松手后图片保持原位（修复前必现全黑）；表情包页没有缩放手感。
